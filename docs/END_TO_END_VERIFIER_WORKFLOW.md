# END_TO_END_VERIFIER_WORKFLOW.md — SyncNode AI/ML Backend Golden Demo

## 0. Purpose

This specification defines the **first complete backend-only, end-to-end verifier workflow** for SyncNode.

The goal is to prove, with one reproducible workflow, that the SyncNode AI/ML backend can:

```text
receive a natural-language request
→ understand the request locally
→ retrieve relevant local knowledge
→ build a structured execution plan
→ choose agents/models/tools by capability
→ execute real local computer actions
→ automatically observe the real Windows screen/application state
→ verify every important postcondition from independent evidence
→ recover from bounded failures without hallucinating success
→ continue only when verification permits it
→ expose live backend events, observations, tool calls, verification, recovery and artifacts
→ finish with a machine-verifiable audit trail
```

This document is the implementation/test contract for the **AI/ML backend milestone only**.

The Electron workbench, polished GUI, marketing shell, and production packaging are intentionally secondary. The backend must be able to drive and verify the demo through API calls, background workers, local runtimes, structured events, and controlled computer automation.

The central rule is:

> **The model proposes. The backend observes. Deterministic infrastructure verifies.**

A model response, tool result, or internal rationale is never itself proof that the real-world action succeeded.

# 1. GOLDEN DEMO REQUEST

The golden test starts from one user request.

Use this exact demo request for the initial integration test:

```text
Write a short original paragraph about a tree standing beside a quiet industrial road, save it as a Word document named SyncNode_Verifier_Demo.docx in the SyncNode demo workspace, open the document in Microsoft Word, verify visually and structurally that the paragraph is present, then create a browser email draft addressed to the demo recipient with the document attached. Recommended deterministic test mode:
```

```text
Generate a 90–140 word original paragraph.
Do not copy source documents.
Do not include confidential information.
Do not mention that the content was generated by an AI system.
```

For repeatable automated testing, the test harness may provide a fixed seed or expected semantic constraints.

Example semantic requirements:

```text

- road
- industrial setting
- quiet/low-activity atmosphere

must be:
- one paragraph
- 90–140 words
- coherent
- non-sensitive
```

The exact prose does not need to be identical on every run unless deterministic seed mode is explicitly enabled.

# 3. TEST PHILOSOPHY

The test is not:

```text
prompt
→ LLM says it finished
→ mark success
```

The test is:

```text
prompt
→ plan
→ perform action
→ observe real environment
→ verify independent evidence
→ persist verified result
→ continue
```

For every major side effect, the backend must answer:

```text
What did we intend to do?
What tool actually ran?
What did the environment actually show?
What deterministic assertion proves the result?
What evidence was captured?
What was the verification result?
What recovery occurred, if any?
Who/what authorized the next action?
```

# 4. NON-HALLUCINATION CONTRACT

The demo must explicitly test resistance to false success claims.

## 4.1 Prohibited success condition

Never allow:

```python
if model_message.contains("done"):
    step.status = "complete"
```

Never allow:

```python
tool_result = {"status": "success"}
```

to automatically prove the real-world postcondition.

The executor's success status means only:

```text
the executor reports that it completed the requested operation
```

It does NOT mean:

```text
the requested real-world state has been proven
```

Only the verification subsystem can promote the action into a verified state.

# 48. VERIFIER DECISION TABLE

For every verification target, define:

| Target | Primary Evidence | Fallback Evidence | PASS condition | FAIL condition |
|---|---|---|---|---|
| DOCX exists | Filesystem | None | Canonical path exists | Missing |
| DOCX readable | Parser | None | parser succeeds | parser fails |
| Paragraph exists | DOCX structure | UI/visual | expected text constraints met | missing/invalid |
| Word open | UIA/process | screenshot | correct window visible | wrong/missing window |
| Word visible content | UIA/document state | visual | content confirmed | absent |
| Browser page | DOM | screenshot | expected page state | wrong page |
| Draft exists | DOM | visual | draft state confirmed | not confirmed |
| Attachment | DOM/upload state | visual | attachment identity confirmed | missing/ambiguous |
| Recipient | DOM/accessibility | visual | exact expected recipient state | mismatch |
| Send safety | Policy state | None | approval required | unapproved send path |

The exact target list can be expanded.

# 49. CONFIDENCE RULES

Use confidence as metadata, not authority.

Example:

```text
deterministic file hash = authoritative
parser success = authoritative
UIA property match = authoritative for that UI assertion
DOM state match = authoritative for that browser assertion
visual model estimate = supporting evidence
model statement = non-authoritative
```

Never implement:

```python
if confidence > 0.9:
    step.status = "complete"
```

without mandatory postcondition checks.

---

# 50. ASSERTION FRESHNESS RULE

Every state-sensitive verification must record:

```text
captured_at
observed_state_id
max_age_ms
```

Example:

```python
if now - observation.captured_at > contract.max_evidence_age_ms:
    raise StaleObservationError(...)
```

The evaluator must capture a new observation rather than quietly using stale evidence.

---

# 51. RECOVERY REPLAN RULE

When replanning is triggered:

```text
DO:
- preserve verified artifacts
- preserve successful ancestor nodes
- preserve immutable audit history
- include failure evidence
- include fresh observation
- regenerate only invalid downstream graph

DO NOT:
- delete verified artifacts unnecessarily
- rerun destructive work blindly
- clear audit history
- reuse stale screen observations
- silently broaden permissions
- switch to public cloud
```
